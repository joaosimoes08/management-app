# Step 24: after measurement (2026-11-21)

Re-run of the exact Step 18 script (`scripts/performance/baseline.mjs` plus the browser probe) on the same dataset and mode. "Before" is the Step 18 run3 (`docs/performance/raw/run3/`, browser `browser-run3.jsonl`); "after" is this run.

## Method

- **Code measured:** `integration/phase-fp` at `bdd5472` (Steps 19, 20, 32, 35 and 36 merged). Step 21 (#117) is **not** included: it isn't merged yet, so its before/after numbers are in the #117 body.
- **Dataset:** the same Step 18 copy (7,768,348 AuditLog rows; `raw/step24/dataset-counts.csv`), on PostgreSQL 18 in a disposable container. All 56 migrations from `bdd5472` were applied to it once, and it was saved as a template. Each stack start creates a fresh `mgmtapp_perf` from that template and flushes Redis, so every run starts from identical data.
- **Mode:** production build (`next start` behind `web-proxy.mjs`, instrumented API `server.cjs`), loopback only, local Keycloak from `local-identity.mjs`. This is the same as Step 18 (G2 default).
- **API:** `node scripts/performance/baseline.mjs --dataset --plans`, 2 passes, 50 sequential + 10 concurrent samples per endpoint, and the search A/B.
- **Browser:** `/__perf/start?runs=5&passes=1`, 10 pages × cold/warm × 5 = 100 samples, on the same probe as Step 18.
- **Machine:** this Mac was shared with other work. Load averages are in `raw/step24/load-average.txt` (1-minute: 4.2–9.8 during the runs). Step 18 didn't record its load average, so the absolute browser comparisons are weaker than the API ones.

### Re-runs and outliers

1. **Global search, pass 1:** 80 of 120 samples returned 429. The warm-up had already used up the global per-IP throttle budget (100 per 60 s) for that route. After a 75 s cool-down I re-ran only `global-search-api` and `global-search-miss` for pass 1 (`PERF_ONLY=global-search-api,global-search-miss PERF_PASSES=1`) and swapped those rows in (`raw/step24/search-rerun-api-raw.csv`). All 3,520 rows in `raw/step24/api-raw.csv` are HTTP 200.
2. **Browser:** run 1 (`browser-run1.jsonl`) came right after the API load test and looked like an outlier. Run 2 (`browser-run2.jsonl`) used a fresh stack and database with nothing running before it. It reproduced the same pattern, so the tables below use **run 2** and run 1 is kept for reference.

## What got worse, and why

1. **⌘K search for "api", 15 → 147 ms.** This is expected, and #113 (Step 20) disclosed it. Before, "api" matched thousands of HTTP_REQUEST audit rows, so the scan stopped early (6,899 bytes of results). Step 20 excludes HTTP_REQUEST rows from global search, so "api" is now a real miss (12 bytes) and costs the same as any other miss: about 150 ms instead of 2.7 s. The worst case improved 17×. The "api" case only looked fast before because it returned audit noise.
2. **Small API endpoints +10 to +24 % (sites, devices, ipam-usage, audit-page, rack-detail, ipam-subnets).** In absolute terms these are 1–3 ms, on endpoints under 20 ms. Pass 1 and pass 2 of this same run differ by up to 46 % on the same endpoints (sites 8.1 → 11.8, audit-page 9.8 → 7.9), so this is within run-to-run noise on a loaded machine. Two have real causes that are small and intended: `devices` runs 2 more SQL queries (19 → 21) and returns 2 % more bytes because of tags (Step 36), and `sites` / `ipam-subnets` return more bytes for the same reason.
3. **Time to data visible on dashboard, /ipam, /rack, /topology and /changes, +27 to +77 % (50–180 ms).** Both browser runs show this. The breakdown in the probe points away from the API:
   - The critical API request time is flat or lower (dashboard 52 → 32 ms; ipam 13 → 18; rack 31 → 33; topology 22 → 28; changes 29 → 49).
   - TTFB is unchanged.
   - Most of the added time is in the Keycloak → identity step before any data request (dashboard 92 → 136 ms, changes 107 → 155, audit 99 → 219) and in client render after the data (+5 to +8 ms).

   The Keycloak step runs in a JVM container on the same CPU, so the 1-minute load average of 6–9 is the likely cause. The UI added to these pages since Step 18 (tags filters, saved views, topology impact) may also add some client time. **Not proven:** a clean A/B on an idle machine (Step 18 build vs `bdd5472`, back to back) is needed to separate the two. Step 21 (#117) removes duplicate setup and topbar calls on these pages; its numbers are in #117.
4. **Dashboard warm bytes −81 % and requests −61 % are not a real cache win.** 3 of the 5 warm dashboard samples were `auth-unavailable`: the page got no token and made 0 API requests, which pulls the median down. The same harness issue appears in Step 18 (2 samples) and in Step 21. I couldn't reproduce it by hand. For the other pages, warm bytes and requests are the same within +5 % (+1 to +3 requests from new UI).
5. **AuditLog writes still about 1 row per authenticated request.** Step 20 removed the HTTP_REQUEST row for reads. But `AuthGuard` calls `AuthService.syncUser` on every request, and that writes an `AUTHENTICATED` audit row (plus a user upsert and a role transaction) each time: 1,847 rows for 1,578 API requests in one browser run. The roadmap's "rows per hour of normal use" goal therefore came out at −50 %, not near 0. A follow-up could record AUTHENTICATED once per session or token (`jti`) and skip the role sync when the roles haven't changed. This needs a G3 audit-policy decision, so I haven't changed it here.
